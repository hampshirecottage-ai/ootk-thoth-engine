# AGENTS.md

Shared rules for AI coding assistants (Claude, Codex, Copilot and others) working in this
repository. People are welcome to read it too. README.md has the full detail; this file is
the short version plus the rules that matter most.

## Goal

OOTK Thoth Engine is a Python 3.11+ engine and FastAPI web app that does the table work of a
Thoth tarot reading (seeded draw, elemental dignities, aspects, Liber 777 correspondences, up
to Book T's full Opening of the Key) and writes it up as one prompt for the user's AI.

Priorities, in this order:

1. **Accuracy.** The calculations and correspondences must match the tradition and the code's
   own documentation (`/method` describes what `rules.py` and `analysis.py` do).
2. **Consistency.** The CLI, web app, prompt and report all go through the same pipeline and
   give the same answer for the same seed and settings.
3. **Performance.** Faster is better, as long as 1 and 2 still hold.

## Setup, run and test

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -c requirements-lock.txt -e ".[dev]"
.venv/bin/python -m pytest -q                       # default suite mocks the database
.venv/bin/uvicorn ootk.web:app --reload --port 8000 # web app on http://localhost:8000
.venv/bin/ootk --spread 12 --seed 12345             # command line
```

- `requirements-lock.txt` pins the versions CI and the live site use. Change it only on purpose.
- Real-database tests: `OOTK_TEST_DB=1 DB_NAME=ootk_test python -m pytest tests/test_db_integration.py`
  against a database built from `database/schema.sql`. CI (`.github/workflows/tests.yml`) runs
  the whole suite on Python 3.12 with a throwaway PostgreSQL 17, so these run on every PR.
- **Prompt snapshots.** `tests/prompt_snapshots/` holds the whole AI prompt for fixed draws.
  After an intended change to the prompt's wording or layout, rewrite them with
  `OOTK_UPDATE_SNAPSHOTS=1 .venv/bin/python -m pytest tests/test_prompt_snapshots.py` and
  check the diff is what you meant. Never update snapshots just to make a failing test pass.
- **Animations.** The SVGs in `static/site/` are generated by `scripts/make_*_animation.py`
  (and `scripts/make_site_images.py` for the favicon and link-preview image). When you change
  a template, page script or engine table that an animation shows or that its tests check,
  rerun the matching script and commit the new SVG with the change.
- Sanity-check a full run: `ootk --spread 12 --seed 12345 ... | tee run.txt` then
  `python scripts/check_run.py run.txt` (see README).

## Where things live

- `src/ootk/report.py`: `analyze_reading`, the one pipeline the CLI and web share, plus the
  prompt and HTML export.
- `src/ootk/rules.py`: the one source of scoring rules (dignities, aspects, orbs).
- `src/ootk/shuffle.py`: the seeded shuffler, the single source of truth for draws.
- `src/ootk/spreads.py`: spread definitions and layout coordinates (aspects are measured on
  the same coordinates the drawings use).
- `src/ootk/web.py`: FastAPI app; `templates/` and `static/js/` for the pages.
- `database/schema.sql`: full schema plus reference data (cards, correspondences, geometry).
- `database/migrations/`: changes waiting to be run on the live database.

Keep these "one source" modules as the only place their logic lives. Don't copy a rule or
table into another module; import it.

## Conventions

- Follow the style of the code around you. Docstrings and comments are plain English and say
  why, not only what.
- A seed must always give the same cards with the same settings, in the CLI and on the web.
  Don't change the shuffle or the draw order without the owner's explicit say-so.
- Thoth is the default mapping (it matches the card pictures); Golden Dawn and French/Egyptian
  are options. Card art is the public-domain 1909 Rider-Waite-Smith deck.
- When behaviour visible on the site changes, update the matching README section and the
  `/method` or `/start` page text in the same PR, so the docs never drift from the code.
- Add or update a test with every behaviour change.
- One change per PR. Keep PRs small enough to review.

## Database changes

- A schema or card-data change goes in `database/migrations/` as SQL that is safe to re-run,
  **and** into `database/schema.sql` in the same PR.
- The live database is updated by the owner, who pastes the SQL into the hosting provider's
  SQL editor and then restarts the web service (the app reads the card tables once at start).
  Never run SQL against the live database yourself, and say in the PR what SQL needs running.
- A backup or snapshot is taken before any migration.

## Guardrails

- **Ask the owner before** editing code or config, pushing, opening a PR, or merging.
  Explaining, reading and running tests locally are fine without asking.
- **Merging to `main` deploys the live site** automatically. `main` is protected: every change
  goes through a PR with passing tests and the owner's review. Never merge on your own.
- **Never rewrite history or force-push** to shared branches, and never change the
  repository's visibility or settings.
- Don't add new dependencies, services or environment variables without asking.
- Don't remove or change features the owner hasn't asked about, even if they look unused.

## Privacy: this repository is public

Everything committed here is visible to anyone, forever (git history keeps it even after a
file is deleted). **Never commit:**

- readings, reports, prompts generated from real questions, AI answers or journal content;
- logs, run captures (`run*.txt`), database dumps or backups;
- personal seeds (a seed reproduces a reading exactly; use dummy seeds such as `12345`);
- `.env` files, database credentials, API keys, tokens or passwords (`.env.example` holds
  names only, with empty values);
- names of querents or other real people. If a person must be mentioned, use initials.

`.gitignore` already covers `output/`, `outputs/`, `reports/`, `readings/`, `private/`, logs,
dumps and key files, and a secret scan runs in CI. Check `git status` and the diff before
every commit anyway. Personal notes go in `private/`, which is ignored. See also SECURITY.md
and README "Keeping readings private".
